# Task 11 — Fraud Feature Engineering and Dataset Preparation

## 1. Objective

Prepare a reproducible, leakage-controlled offline dataset for the Sentinel fraud model. This task does **not** train a model, create predictions, or change the Kafka consumer. Random Forest training and evaluation are a separate next task.

## 2. Source cohort

The default offline training cohort is the larger labelled synthetic CSV export generated by `app.generate_synthetic_data`. Task 11 reads `accounts.csv` to resolve canonical account types and `transactions.csv` for events and labels. It checks the dataset type, required columns, unique transaction IDs, account references, self-transfers, positive finite amounts and row count against `metadata.json`. It does not require PostgreSQL. A legacy PostgreSQL source remains available explicitly with `--source postgres`.

The current project has a useful distinction in its persistence path:

- `seed_database()` stores the initial labelled synthetic transactions without outbox rows.
- `persist_live_transfer()` stores each continuously generated live transaction and its outbox event atomically.

Task 11 selects transaction rows that have no matching `outbox_events.aggregate_id`. This excludes the live simulator stream, whose current transactions are all normal-labelled, from silently overwhelming the small labelled seed cohort.

This is a project-specific source convention, not a universal data-provenance standard. If another ingestion path later inserts historical transactions without outbox rows, this cohort query must be revised or replaced with an explicit source/provenance column.

The synthetic labels are controlled ground truth generated by our simulator. They are not verified real-bank fraud outcomes.

## 3. Feature set

| Feature | Meaning |
|---|---|
| `amount` | Transfer amount |
| `log_amount` | `log(1 + amount)` |
| `currency` | Transaction currency |
| `transaction_type` | Transaction type |
| `channel` | UPI, IMPS, NEFT, RTGS or INTERNAL |
| `transaction_hour` | UTC hour of the transaction |
| `day_of_week` | UTC weekday, Monday = 0 |
| `sender_account_type` | Sender account category |
| `receiver_account_type` | Receiver account category |
| `sender_txn_count_1h` | Earlier sender transactions in the preceding hour |
| `sender_txn_count_24h` | Earlier sender transactions in the preceding 24 hours |
| `sender_amount_sum_24h` | Earlier sender transfer amount in the preceding 24 hours |
| `sender_unique_recipients_24h` | Distinct recipients in the preceding 24 hours |
| `receiver_txn_count_24h` | Earlier incoming transfers to receiver in the preceding 24 hours |
| `sender_avg_amount_30d` | Earlier sender average transfer amount in the preceding 30 days |

All historical windows are open at the target timestamp: only records with timestamps strictly earlier than the target event are eligible. Events sharing an identical timestamp are evaluated against the same history snapshot, so an arbitrary row order cannot make one simultaneous event a feature of another.

## 4. Leakage controls

The model input allowlist is explicitly defined in `fraud_features.py`.

Excluded from model inputs:
- Transaction, sender-account and receiver-account identifiers.
- `is_aml_suspicious`, `fraud_scenario`, and `aml_typology`.
- Sender and receiver post-event balance snapshots, including before/after balance fields.
- The fraud target `is_fraud` is emitted only as the target column, never as an input feature.
- Dataset partition `dataset_split` is metadata, not a model feature.

The current feature set uses event attributes, account categories, and strictly prior transaction history. It does not use a future event, model prediction, AML result, or post-event balance.

## 5. Chronological partitions

Rows are ordered by event timestamp and transaction ID, then assigned:
- First 70%: training.
- Next 15%: validation.
- Final 15%: test.

Historical features for later partitions can use earlier transactions from the same seed cohort. This reflects the information available at the later event time and does not expose future records. No random shuffle is applied.

The validator reports normal/fraud counts for every partition. It warns if a partition has no positive or no negative examples; it does not fabricate class balance or silently move events between time periods. With a small synthetic cohort, a warning is a real limitation, not a test failure.

## 6. Input and output

Default input: `backend/data/raw/synthetic/` (`accounts.csv`, `transactions.csv`, `metadata.json`). `customers.csv` is retained as part of the shared bank export but is not needed to calculate the current transaction features. The loader uses only `is_fraud` as the target; AML labels and scenario columns are deliberately ignored.

Default output remains `backend/data/processed/fraud/fraud_dataset.csv` and `fraud_dataset_metadata.json`. Output metadata records source parameters and counts so the prepared dataset can be traced to its generator run.

## 7. Files

| File | Purpose |
|---|---|
| `backend/app/services/fraud_features.py` | Point-in-time feature engineering and feature allowlist |
| `backend/app/services/fraud_dataset.py` | Offline CSV loading, PostgreSQL legacy extraction, orchestration and CSV/JSON export |
| `backend/app/services/fraud_dataset_validation.py` | Strict schema checks, numeric checks, chronological split and class summary |
| `backend/app/prepare_fraud_dataset.py` | CLI entry point; defaults to offline CSV |
| `backend/tests/test_fraud_features.py` | Historical-window and feature-leakage tests |
| `backend/tests/test_fraud_dataset.py` | Cohort selection, splitting, validation and export tests |

No new Python dependency is required; the implementation uses the standard library and existing SQLAlchemy database layer.

## 8. Run

From the repository root, ensure PostgreSQL is running and the database has been seeded:

```powershell
cd backend
python -m app.prepare_fraud_dataset
```

The command writes:
- `backend/data/processed/fraud/fraud_dataset.csv`
- `backend/data/processed/fraud/fraud_dataset_metadata.json`

To select another input or output directory:

```powershell
python -m app.prepare_fraud_dataset --input-dir data/raw/synthetic --output-dir data/processed/fraud\n\nTo use the legacy PostgreSQL seed cohort instead, pass `--source postgres`.
```

The metadata file records cohort size, class counts, split counts, warnings, feature names, target name and excluded columns. The generated CSV is an artifact; it is not committed as source code.

## 9. Tests and evidence boundary

Run the full test suite from the repository root:

```powershell
python -m pytest
```

SQLite-backed tests validate query semantics, feature calculations, split assignment, schema validation and file export. They do not prove the live PostgreSQL dataset has a particular row count; run the CLI against the local PostgreSQL database to verify that environment.

## 10. Limitations and next task

- The default generator export contains 21,999 synthetic transactions, including 1,000 fraud-positive labels (one is also AML-positive). These are configured synthetic counts, not real-world prevalence.
- Synthetic labels and synthetic behaviour do not establish real-world fraud detection performance.
- The chronological test partition must be inspected for positive and negative examples. Metrics in the next task must be interpreted with class counts and uncertainty visible.
- The current model feature set is transfer-focused. It does not include device, merchant, login, geolocation, card-present or customer-KYC features.
- This task does not train a model. Task 12 will train and evaluate the Random Forest pipeline using this prepared dataset.
