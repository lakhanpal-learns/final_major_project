# Phase 01 — Task 02: Shared Banking Registry

**Status:** Implemented in repository; local test verification pending  
**Date:** 2026-11-26

## Objective

Create one canonical synthetic customer and bank-account registry for Sentinel. Fraud and AML processing must refer to the same Sentinel customer IDs and account IDs; they must not independently invent or join unrelated PaySim/AMLSim identifiers.

## Implemented

- Added immutable Pydantic Customer and Account domain models.
- Added a deterministic registry builder using Python's standard library.
- Generated stable-format customer IDs such as CUST000001.
- Generated stable-format account IDs such as ACC00000001.
- Generated unique synthetic account numbers.
- Assigned every account to an existing canonical customer.
- Created one account per customer and a second account for every tenth customer to exercise one-to-many ownership.
- Added seeded generation so the same customer count and seed produce repeatable records.
- Added lookup methods by canonical customer ID and account ID.
- Added tests for counts, uniqueness, referential integrity, reproducibility, lookups and invalid input.

## Design decisions

- The registry is in-memory for this task. PostgreSQL persistence is intentionally deferred to the database integration task.
- IDs are generated by Sentinel and form the identity boundary shared by fraud and AML.
- Synthetic customer names and cities are fixture data, not real customer records.
- A fixed seed makes local development and tests reproducible. A different seed can produce a different synthetic registry; do not regenerate IDs independently inside separate fraud and AML pipelines.
- This task does not yet create transactions, publish Kafka events, or expose customer/account API routes.
